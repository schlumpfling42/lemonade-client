# Coding Subgraph Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let the agent run multi-step coding jobs through a `coding` subgraph — environment → investigate → plan → review → user plan approval → implement → verify — with the approved plan enforced by the graph and live progress in the window.

**Architecture:** A new annotated graph class `CodingGraph` (package `net.rka.ai.agent`, generated by `graph-processor` like `ApprovalGraph`) is added to `AgentGraph` as the `coding` subgraph node. The model starts it by calling the tool `startCodingJob(goal)`; the main router routes that call to `coding`. All job data lives in new `AgentGraph.State` keys; the plan-approval pause is a LangGraph4j interrupt before the inlined node `coding-planApproval`; `Agent.run` switches to `graph.stream(...)` to report progress.

**Tech Stack:** Java 27, LangChain4j 1.22, LangGraph4j 1.9.5, project annotations + `graph-processor`, Jackson, JavaFX 27, JUnit 6.

**Spec:** `docs/superpowers/specs/2026-10-18-coding-subgraph-design.md`

## Global Constraints

- Use LangGraph4j mechanisms (state keys, nodes, routers, subgraphs, interrupts, streaming); no side channels (CLAUDE.md, memory "use the graph").
- Plan approval covers **only** the plan's commands and file changes, **only inside the trusted folder**, and ends with the job.
- A tool call during implement that the plan doesn't cover never runs; the job goes back to `plan` → `review` → user approval.
- Plan commands match by **exact** whitespace-normalized text **and** working directory; **no wildcards**; a planned command may run any number of times.
- File entries: `create`/`modify` (file, or folder = path ending in `/` covering everything under it), `delete`, `move`; delete/move only on entries of that kind; a folder entry never allows deleting/moving the folder itself.
- The user's trusted commands (global + conversation) still run during a job without being in the plan.
- Investigate may run, without asking, only the fixed probe list (exact match) or the user's trusted commands.
- Verify: at most **3** attempts per job (re-plans don't reset); then report.
- Coding job commands use `CODING_COMMAND_TIMEOUT_SECONDS` (default **600**); probes use a short timeout (**20 s**).
- Environment cache: `environment.json` next to the global settings file (`~/chat/environment.json` by default), stale after **7 days**, refreshed when stale or when verify output shows a missing tool.
- SSH (`runRemoteCommand`) and memory tools (`remember`/`forget`) are **not offered** inside a coding job (my call: not covered by the spec's folder rule).
- Keep `docs/agent-graph.md`, the README diagram and the `AgentGraph` Javadoc in sync.
- This folder is **not a git repository**: tasks end with a passing build instead of a commit. Build/test command: `.\gradlew.bat build` (Windows) — expected `BUILD SUCCESSFUL`.

## Review Focus

1. A planned command called with a `workingDirectory` outside the folder (`..`, absolute path) — must be refused even though the command text matches (Task 1 test `commandOutsideFolderIsNotCovered`).
2. The model wraps the plan JSON in a Markdown code fence or adds prose around it — must still parse; truly invalid JSON gets one retry, then the job reports the failure (Task 1 `parsesFencedJson`, Task 3 `invalidPlanTwiceEndsJob`).
3. The model never finishes a step (keeps calling tools, or answers without doing anything) — a per-step limit of **15** model turns ends the job with a report instead of hanging (Task 4 `stepTurnLimitEndsJob`).
4. Verify fails because a tool isn't installed ("not recognized" / "command not found") — counts as a failed attempt and marks the environment cache stale (Task 5 `missingToolMarksEnvironmentStale`).
5. The user picks **Revise** several times — every revision must return to the plan approval pause, and Deny afterwards must leave the folder untouched (Task 6 `reviseThenDenyChangesNothing`).

### Task 3: `CodingGraph` part 1 — environment, investigate, plan, review, approval routing

**Files:**
- Create: `src/main/java/net/rka/ai/agent/CodingGraph.java`, `src/main/java/net/rka/ai/agent/CodingPrompts.java`
- Modify: `src/main/java/net/rka/ai/agent/AgentGraph.java` (State keys + getters only), `src/main/java/net/rka/ai/tools/ToolRegistry.java` (filtered specifications)
- Test: `src/test/java/net/rka/ai/agent/CodingGraphTest.java`

**Interfaces:**
- Consumes: `CodingPlan` (Task 1), `EnvironmentInfo` (Task 2), `ToolCallRunner.run(..., timeoutSeconds)`.
- Produces:
  - `AgentGraph.State` keys (all `static final String`, values stored as String/Integer): `CODING_GOAL = "codingGoal"`, `CODING_CALL_ID = "codingCallId"`, `CODING_ENVIRONMENT = "codingEnvironment"`, `CODING_MESSAGES = "codingMessages"` (appender channel, added to `SCHEMA`), `CODING_START = "codingStart"` (index into `codingMessages` where this job begins), `CODING_FINDINGS = "codingFindings"`, `CODING_PLAN = "codingPlan"` (JSON), `CODING_DECISION = "codingDecision"` (`approve` / `revise` / `deny`), `CODING_COMMENT = "codingComment"`, `CODING_REVISION_REASON = "codingRevisionReason"`, `CODING_STEP = "codingStep"`, `CODING_STEP_TURNS = "codingStepTurns"`, `CODING_ATTEMPTS = "codingAttempts"`, `CODING_VERIFY_OUTPUT = "codingVerifyOutput"`, `CODING_REPORT = "codingReport"`, `CODING_PLAN_ERRORS = "codingPlanErrors"`; typed getters on `State` for each (e.g. `Optional<CodingPlan> codingPlan()`, `List<ChatMessage> codingMessages()` returning only this job's part from `CODING_START`).
  - `ToolRegistry.specifications(Predicate<String> toolName)`.
  - `CodingGraph` (`@Graph(name = "coding", state = AgentGraph.State.class, serializer = LANGCHAIN4J)`), constructor `CodingGraph(ChatModel model, ToolCallRunner toolCalls, NodeTracing tracing, EnvironmentInfo environment, int timeoutSeconds)`; `static final String START_TOOL = "startCodingJob"`; node names exactly: `environment`, `investigate`, `investigateTools`, `plan`, `review`, `planApproval`, `implement`, `implementTools`, `verify`, `report`. In this task `implement` and `verify` are stubs that route to `report` (Task 4/5 fill them in).
  - Edges/routers: START → environment → investigate; investigate router: tool calls → investigateTools → investigate, no tool calls or 6 rounds → plan; plan → review; review router: valid plan → planApproval, invalid twice → report; planApproval router on `CODING_DECISION`: approve → implement, revise → plan, deny → report.
  - `CodingPrompts`: one `String` constant per phase (`INVESTIGATE`, `PLAN`, `REVIEW`, `IMPLEMENT`) containing the plan JSON schema from Task 1 and the review rules from the spec (missing steps, order, OS/shell from the environment, non-interactive flags, every path inside the folder, every command with a working directory).
  - `environment` node: finds the `startCodingJob` call among `state.unansweredToolCalls()`, stores goal/call id, `CODING_START = codingMessages().size()`, step 0, attempts 0, environment summary; answers any **other** unanswered calls of the same AI message with an error result ("Not run: a coding job started; ask again afterwards").
  - `investigateTools`: offers/allows read-only tools + `runCommand` only for `EnvironmentInfo.isProbe` or user-trusted commands; anything else gets an error result listing the probe commands.
  - `plan`: model → `CODING_PLAN` (normalized JSON via `CodingPlan.parse(...).toJson()`); a parse error is stored in `CODING_PLAN_ERRORS` and counted; on revision the prompt includes the previous plan, done steps, `CODING_COMMENT` and `CODING_REVISION_REASON`.
  - `review`: model returns the corrected plan JSON (same parsing); `planApproval` node itself does nothing (the interrupt happens before it).

# Skills — design

Date: 2026-10-25 · Status: approved ("create plan and implement")

## Intent

Today every capability of the agent is Java code: a new multi-step workflow (like the coding job) means
a new annotated graph class, a rebuild and a restart. The user wants to add workflows **without writing
Java**: a **skill** is a JSON file in a folder that describes a subgraph — its steps, prompts, which
tools it may use, where it pauses for the user and how it branches — and the agent picks it up and adds
it to its graph. Writing that JSON by hand is error-prone, so a **skill builder** creates it from a
description in chat, checks it, and saves it after the user approves.

Typical skills: "review this file against our checklist", "summarize the last commits and draft release
notes", "research a library on the web and write notes", "triage a bug report: reproduce, locate, propose
a fix".

## Goals

1. A skill is one JSON file in `~/chat/skills/` (next to `settings.json`). Valid skills are added to the
   agent graph as subgraphs; the model starts one by calling its tool, like `startCodingJob`.
2. Skills use **fixed node kinds** provided by the app (no Java code, no scripts): ask the model, run
   tools, pause for the user, branch, set values, finish.
3. Skills **can use tools** — the existing ones, by name — under the **existing safety rules**.
4. A **skill builder** turns a description into a valid skill file: draft → validate → fix → show to the
   user → save on approval. Invalid files never become part of the graph.
5. Skills show in the window like coding jobs: live progress, tool pills, thinking, a final result.
6. Adding, changing or removing a file takes effect on the next turn after a reload, without restart.

## Non-goals

- No code in skills (no Java, JavaScript, shell snippets as node logic). Commands only through the
  `runCommand` tool, with its approval rules.
- No skills calling other skills or starting coding jobs (no nesting) in this version.
- No sharing/marketplace, versioning or signing of skill files.
- No editing skills in a visual editor (the builder and a text editor are the ways to change them).

## Anti-goals (failure even if it "works")

- **A skill as a way around approvals.** A skill must never run a tool that would need approval in the
  main graph without the same approval (risky commands, writes outside trusted rules, anything after web
  content). A skill file can only narrow what a skill may do, never widen it.
- **A broken file breaking the app.** One bad skill must not stop the agent from starting or other
  skills from loading.
- **Hidden behavior.** The user must be able to see what a skill does (its steps as a diagram, its
  prompts, its tools) before it's saved and whenever it's listed.

## Constraints

- Use LangGraph4j mechanisms (state keys, nodes, routers, subgraphs, interrupts, streaming); no side
  channels (CLAUDE.md, memory "use the graph"). Skills are real subgraphs in the compiled graph.
- The main graph is generated by `graph-processor` from annotations; skills need a small, general
  extension of it (below), not hand-written graph wiring in `AgentGraph`.
- Keep `docs/agent-graph.md`, the README diagram and the `AgentGraph` Javadoc in sync (CLAUDE.md); loaded
  skills are documented by a diagram the app generates (below).
- Context budget: prompts go through `ContextFittingChatModel`; skill transcripts must stay bounded.
- Not a git repository: tasks end with a passing `.\gradlew.bat build`.

## Design (my calls unless marked above)

### Where skills plug into the graph

```
START -> memory -> agent --(skill_<name> call)--> skill-<name> -> agent
                         --(startCodingJob)-----> coding -> agent
                         --(… existing routes …)
skill-<name> = subgraph built from ~/chat/skills/<name>.json:
  start -> (the file's nodes and edges) -> finish -> END
           + toolApproval (built in, pause)   for tool calls that need approval
           + userInput    (pause)             where the file asks the user
```

- **Graph-processor extension** (my call): a new annotation `@Subgraphs(prefix = "skill-", returnTo =
  "agent", router = "route")` on an `AgentGraph` method returning `Map<String, StateGraph<State>>`. The
  generated `stateGraph(...)` adds each entry as node `skill-<name>`, an edge back to `agent`, and merges
  `skill-<name> → skill-<name>` into the router's route map. The generated outline lists
  `skill-* = subgraphs skills()`. This keeps skills graph-native and reusable for other dynamic parts.
- `AgentGraph.route`: a call named `skill_<name>` (checked after `startCodingJob`) → `"skill-<name>"`.
  Other calls in the same reply are answered "Not run", exactly like the coding job does.
- Each skill is its own subgraph built at load time by `SkillGraphBuilder` from the JSON; node ids are
  inlined as `skill-<name>-<node>`, so interrupts can target them.
- **Reload** (my call): skills are loaded at startup and on **Reload skills** (window menu/Settings, and a
  `/reload-skills` CLI flag). Reloading recompiles the agent graph between turns (the compiled graph is
  per `Agent`; a turn in progress keeps the old one). Changes never apply in the middle of a turn.

### The skill file

One JSON object (schema in `SkillFile`; validated before use):

```json
{
  "name": "release-notes",
  "description": "Draft release notes from the recent commits of the trusted folder. Use when the user asks for release notes or a changelog.",
  "inputs": [ { "name": "since", "description": "tag or date to start from", "required": false } ],
  "limits": { "maxSteps": 40, "maxToolRounds": 8 },
  "nodes": [
    { "id": "collect", "kind": "model", "prompt": "Collect the commits since {{input.since}} ...",
      "tools": ["runCommand", "readFile"], "output": "commits", "next": "draft" },
    { "id": "draft", "kind": "model", "prompt": "Write release notes from:\n{{commits}}", "output": "notes",
      "next": "check" },
    { "id": "check", "kind": "askUser", "question": "Release notes draft:\n\n{{notes}}",
      "choices": ["accept", "revise", "cancel"], "output": "answer",
      "on": { "accept": "done", "revise": "draft", "cancel": "cancelled" } },
    { "id": "done", "kind": "finish", "result": "{{notes}}" },
    { "id": "cancelled", "kind": "finish", "result": "Cancelled by the user.", "error": true }
  ],
  "start": "collect"
}
```

- **Wiring by outcomes** (my call, needed to express the coding job): every node kind has named
  **outcomes**; a node maps them to the next node with `"on": {"<outcome>": "<node id>"}`, or uses
  `"next"` when the kind has a single outcome. `askUser`'s outcomes are its choices; `branch`'s are its
  `cases` targets plus `otherwise`; `model` has `done` (plus `stopped` on an error or limit, which every
  kind has and which defaults to an automatic error finish when not mapped); `finish` has none. The
  validator checks every outcome of a node is mapped (except `stopped`).

- **name**: lower-case letters, digits and `-`, unique; becomes the tool `skill_<name>` (dashes → `_`)
  and the node `skill-<name>`. **description**: the tool description the model reads to decide when to
  use it (required, ≥ 20 characters). **inputs**: the tool's parameters (strings), available as
  `{{input.<name>}}`.
- **Templates**: `{{var}}`, `{{var.field}}` (JSON values), `{{input.x}}`, plus built-ins `{{goal}}` (the
  call's arguments as text), `{{folder}}` (trusted folder), `{{environment}}` (the cached environment
  summary). Unknown variables are a validation error; values are inserted as text (no expression language).

### Node kinds (fixed, provided by the app)

| kind | What it does | Fields |
|------|--------------|--------|
| `model` | Asks the model with `prompt` (system prompt = the skill's description + a fixed skill preamble). With `tools`, it is a ReAct loop: tool calls go to the built-in tool step and come back, until the model answers without calls or `maxToolRounds` is reached. The final text goes to `output`. `format: "json"` parses it (one retry on invalid JSON, then the skill finishes with an error). | `prompt`, `tools` (names), `output`, `format` (`text`/`json`), `thinking` (show or hide streamed text: `shown` default, `progress` like the plan step) |
| `askUser` | Pauses (interrupt) and asks the user: a question with buttons (`choices`) and an optional comment. The answer goes to `output` as `{choice, comment}`. | `question`, `choices`, `output` |
| `branch` | Routes on values: first matching case wins, else `otherwise`. Conditions: `equals`, `notEquals`, `contains`, `matches` (regex), `isEmpty`, `count` comparisons on lists, `and`/`or`. | `cases`, `otherwise` |
| `set` | Sets variables from templates (e.g. counters via `{"increment": "rounds"}`, lists via `append`). | `values` |
| `finish` | Ends the skill: `result` (template) becomes the `skill_<name>` call's result, flagged as an error when `error: true`. Every path must reach a `finish`. | `result`, `error` |

Built into every skill subgraph (not written in the file): `toolStep` (runs the model node's calls) and
`toolApproval` (the approval pause), see below.

### Built-in skills: coding (decided: convert coding; approval and trusted stay core)

- **coding becomes a skill file**, `coding.json`, shipped read-only in the app's resources
  (`net/rka/ai/agent/skills/coding.json`) and loaded like any skill. It holds the job's wiring (which step
  follows which outcome), its limits (`maxInvestigateRounds` 6, `maxStepTurns` 15, `maxVerifyAttempts` 3,
  `maxDesignRounds` 2, `maxPlanAttempts` 2) and its prompts (today's `CodingPrompts` texts move into the
  file; the code keeps no copy).
- Its steps are **coding node kinds** — Java, part of the app, one per current `CodingGraph` node with
  the same behavior and the same outcomes: `coding.environment`, `coding.investigate` (outcomes `tools`,
  `plan`), `coding.investigateTools` (`investigate`), `coding.plan` (`review`), `coding.review`
  (`approval`, `retry`), `coding.planApproval` (pause; `approve`, `revise`, `deny`), `coding.implement`
  (`tools`, `next`, `verify`), `coding.implementTools` (`implement`, `revise`), `coding.verify`
  (`passed`, `fix`, `failing`), `coding.designReview` (`fix`, `done`), `coding.report` (finish). Each
  also has `stopped`. The safety-critical parts — the plan check, what investigate may run, the plan
  approval pause, verify — stay in these kinds, so no file can weaken them: a kind always enforces its
  rules, whatever the wiring. The validator additionally requires that a skill using
  `coding.implementTools` reaches it only after `coding.planApproval`'s `approve`.
- `CodingGraph` stops being an annotated graph: its node methods become the implementations of these
  kinds (the `coding*` state keys, `CodingPlan`, design guides, plan files, live output and progress are
  unchanged). The node ids become `skill-coding-<node>` (e.g. `skill-coding-planApproval`), and
  `NodeTracing` names `skill/coding/<node>`; `Agent`, `LiveChannel`, progress and the tests use those.
- The tool stays **`startCodingJob(goal)`**: a skill file may name its tool with `"tool"` (built-in
  skills only, my call, so user skills can't shadow core tools); others get `skill_<name>`.
- **Overriding a built-in:** a user file `~/chat/skills/coding.json` (written through the builder)
  replaces the built-in one; it can change prompts, limits and wiring but not the kinds' rules. Invalid →
  the built-in one is used and the error is listed.
- **approval** and **trusted** remain annotated `@Subgraph`s of `AgentGraph` (unchanged).

### Tools in skills — the safety rules (anti-goal 1)

- A `model` node offers **only** the tools it lists, and only tools that exist in the registry; the
  validator rejects unknown names. `startCodingJob`, `skill_*`, and SSH tools are never available in
  skills (my call, like coding jobs). Memory tools (`remember`/`forget`) are allowed only if listed.
- A call to a tool the node didn't list is answered with an error result and never runs.
- Every call goes through the **same rules as the main graph** (`ToolRegistry.needsApproval` /
  `isTrusted`): read-only tools run; `@RequiresApproval` and `@WritesFiles` tools run when trusted
  (global + conversation trusted commands, `tool:` entries); otherwise the skill **pauses at
  `toolApproval`** and `Agent` asks with the existing approval dialog (same `Approver.review`, same
  "Always" options). After web content in the turn or in the skill's transcript, nothing guarded runs
  unasked. File tools stay confined to the trusted folder.
- Unlike a coding job, a skill has no plan approval: approvals are per call (my call; a skill that
  changes many files can tell the model to batch, or the user trusts the tool for the conversation).

### State (new keys in `AgentGraph.State`)

`skillName`, `skillCallId`, `skillMessages` (appender with duplicates, the skill's transcript, separate
from `messages` like `codingMessages`), `skillStart` (index into `skillMessages`), `skillVars` (JSON
object string: inputs, outputs, set values), `skillNode` (current node id, for resuming after a pause),
`skillSteps` (nodes run, against `maxSteps`), `skillToolRounds`, `skillAnswer` (written by `Agent` on
resume from `askUser`: `{choice, comment}`), `skillResult`. The skill's start node resets them.

### Limits (my calls)

- `maxSteps` default 40 (hard cap 200): node visits per run; exceeding it finishes with an error result
  ("stopped: too many steps"). `maxToolRounds` default 8 per `model` node visit.
- A model or tool exception inside a skill finishes it with an error result (like the coding job's
  `stopped` route), so the conversation keeps a record; the turn itself doesn't fail.
- The skill transcript given to each `model` node is that node's own conversation (prompt, its tool
  calls and results), not the whole skill history; values flow between nodes only through variables.
  This keeps prompts small and the file's data flow explicit.

### Loading and validation

`SkillLoader` reads `~/chat/skills/*.json` at startup and on reload:
- Parse against the schema; check names, unique node ids, `start`, every edge/branch target exists,
  every node reachable from `start`, every path reaches a `finish`, every template variable is defined
  by an input, a built-in or an earlier node's `output` on every path to it (my call: a simple
  data-flow check over the graph), tool names exist and are allowed, limits in range.
- Valid files become subgraphs; invalid ones are skipped and listed with their errors (window: a
  "Skills" section in Settings with each skill's status; CLI: printed at start). One bad file never
  stops the others or the app.

### Pauses in `Agent`

`Agent`'s pause loop already branches on the paused node id. It gains two generic cases:
`skill-<name>-toolApproval` → the existing tool approval; `skill-<name>-<askUser node>` → a new
`Approver.askUser(SkillQuestion)` (default: the first choice is never assumed; the CLI prints the question
and choices; the window shows a dialog like the plan dialog with Markdown, buttons and a comment).
The compile config's `interruptBefore` list is built from the loaded skills.

### Live output and progress

- `LiveChannel`/`NodeTracing` already know the running node: skill nodes are named
  `skill/<name>/<node>`. `model` nodes with `thinking: "progress"` show "<skill>: <node>… n characters"
  instead of streamed text; others stream like the agent. Tool calls show as pills; their output streams.
- `Agent.progressOf` reports skill nodes as `"<skill name> · <node id>"` (phase) with the last command as
  detail; the window's progress card shows it like a coding job.

### The skill builder

A built-in tool `buildSkill(description)` routed to a built-in **Java** subgraph `skillBuilder` (my call:
the builder is part of the app, so it can't be broken by a bad skill file):

```
skillBuilder: tools (list of available tools with descriptions, node kinds, schema, an example)
  -> draft (model: write the skill JSON for the description)
  -> validate (SkillLoader's validator, no model)
       --errors, < 3 attempts--> draft (with the errors)
       --errors, 3rd attempt---> finish with the errors (nothing saved)
       --valid--> ⏸ review (user: Save / Revise with comment / Cancel)
             save   -> write ~/chat/skills/<name>.json (refuses to overwrite unless the user chose "Replace")
                       -> reload skills after the turn -> finish ("skill_<name> is ready")
             revise -> draft (with the comment)
             cancel -> finish (nothing saved)
```

- The review dialog shows the skill as the user can judge it: name, description (when the model will use
  it), inputs, the **diagram** (Mermaid rendered as an image is out of scope; a text outline of nodes and
  routes, generated by `SkillDiagram`), each node's prompt, and the **tools it may use, with which of them
  need approval**. The raw JSON is one click away ("Show JSON").
- Editing an existing skill: `buildSkill` with "change skill X so that …" loads the file as the starting
  draft; saving replaces it after "Replace" is confirmed.
- Saving writes outside the trusted folder; this is allowed only through the builder's review step
  (an explicit user action), never by a skill or a normal tool.

### Docs

- `docs/agent-graph.md`: the `skill-*` dynamic subgraphs and the `skillBuilder` subgraph in the diagram
  and node table, the new state keys, the processor extension.
- `SkillDiagram` also writes `~/chat/skills/<name>.md` (generated, not read back) with the Mermaid
  diagram, prompts and tools of each loaded skill, so the user can read every skill in one place.
- README: "Skills" section — file location, node kinds, safety rules, the builder, reload.

### Tests (my call, the builder decides details)

- Validator: each rule with a failing file (unknown node kind, dangling edge, unreachable node, path
  without finish, undefined variable, unknown/forbidden tool, bad name).
- `SkillGraphBuilder` + fake model: a skill with model → branch → askUser → finish runs, pauses and
  resumes through `Agent`; tool calls needing approval pause at `toolApproval`; unlisted tools are refused;
  `maxSteps` stops a loop.
- Processor: `@Subgraphs` generates nodes, edges and route entries (a processor test like the existing
  ones).
- Builder: invalid draft → errors back → valid draft → review → save writes the file; cancel writes nothing.

### Settled after the builder check (my calls)

- **Tool specs for skills:** `ToolRegistry` builds specs only from `@Tool` methods, so it gains a way to add
  `skill_<name>` specifications (name, description, string parameters) from the loaded skills, executed
  never (the router catches them, like `startCodingJob`). They are added to `CodingGraph.NOT_IN_JOB`'s
  rule (no skills inside coding jobs) and are never offered inside a skill.
- **Reload:** the compiled graph and the skill tool list are swapped together between turns (turns run
  one at a time); `Agent.graph` stops being final for that.
- **Node ids:** skill names may contain dashes, so ids are never split by string: `SkillLoader` keeps a
  map from inlined node id (`skill-<name>-<node>`) to (skill, node), used by the pause loop, progress and
  `MessageFeed`/`LiveChannel`. The validator rejects names whose ids would collide.
- **Places that know only coding transcripts** read `skillMessages` too: the web-content check
  (`webContentInTurn`), the no-progress `Pause` check, the open calls at an approval pause, `MessageFeed`.
- **CLI:** skills load at start (status printed); there is no reload flag (one question per run).
- **`askUser` dismissed** (dialog closed, end of input in the CLI, a failing approver, the default
  `Approver`): the skill finishes with an error result ("cancelled by the user"); it is never treated as an
  empty answer, so it can't fall into an `otherwise` branch.
- **Skill files only through the builder:** file tools refuse paths inside `~/chat/skills` even when the
  trusted folder contains it.
- **`maxToolRounds` reached:** that node gets one last model call without tools (like the agent's round
  cap); its text becomes the output.
- **Names:** the file name must equal `name` + `.json`; duplicates or mismatches are invalid (listed).
- **Optional inputs** default to "".
- **Builder attempts:** 3 invalid drafts per review round; a Revise starts a new round of 3.

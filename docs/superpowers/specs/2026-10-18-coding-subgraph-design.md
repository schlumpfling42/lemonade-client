# Coding subgraph — design

Date: 2026-10-18 · Status: draft for approval

## Intent

The agent should be able to take on multi-step coding jobs in the conversation's trusted folder,
the kind of work the user actually asks for:

- "create a Java project"
- "create the frontend SvelteKit project"
- "add a LangGraph graph"
- "improve the design"

Today every file write and every command asks for approval one by one, which makes such jobs
impractical, and nothing makes the agent look before it acts or check its work afterwards. The
coding subgraph turns a job into a fixed pipeline — **investigate → plan → review → user approval →
implement → verify/test** — where the user approves **one plan** instead of dozens of calls, and
the graph guarantees the plan is followed.

## Goals

1. The agent decides by itself when a request is a coding job and enters the pipeline.
2. Investigate before planning; plan before changing anything; the model reviews its own plan.
3. One approval: the user sees the reviewed plan and chooses **Approve**, **Revise** (with a
   comment) or **Deny**. Approving pre-approves exactly the commands and file changes listed in the
   plan, and only inside the trusted folder.
4. The plan is **enforced by the graph**: during implementation, a tool call that isn't covered by
   the approved plan does not run; the job goes back to planning and the user gets a revised plan.
5. After implementing, the job verifies (build/tests) and fixes failures, at most **3** attempts,
   then reports what's still broken.
6. **Live progress** in the chat window while a job runs (phase, step n/m, current command,
   verify attempt).

## Non-goals

- No multi-agent setup or parallel workers; one model, one pipeline.
- No git operations unless they're steps in an approved plan (no automatic commits or pushes).
- No visual checking of UI designs ("improve the design" is verified by build/check commands only).
- No new model or provider; the same Lemonade model and tools are used.

## Anti-goals (failure even if it "works")

- **Not following the plan**: running commands or changing files the user didn't approve, or
  silently skipping steps. The design makes this structurally impossible rather than relying on
  the model's good behavior.
- Approvals leaking out of the job: a plan approval must not trust anything after the job ends,
  and never anything outside the trusted folder.

## Constraints

- Follow the project rule: **use LangGraph4j mechanisms** (state keys, nodes, routers, subgraphs,
  interrupts, streaming) instead of side channels or custom plumbing. The subgraph is declared with
  the project's graph annotations (`@Graph`, `@Node`, `@Router`, `@Subgraph`, …) and generated by
  `graph-processor`, like `ApprovalGraph` and `TrustedGraph`.
- Existing safety rules stay as they are outside the job: file tools confined to the trusted folder,
  `@RequiresApproval` / `@WritesFiles` / web-content rules, trusted commands.
- Windows/PowerShell and Linux/bash both have to work (commands come from the model, which already
  knows the shell via `systemInfo`).
- Keep `docs/agent-graph.md`, the README diagram and the `AgentGraph` Javadoc in sync (CLAUDE.md).

## Decided with the user

| Question | Decision |
|----------|----------|
| How a job starts | **The agent decides** (no mode switch or prefix). |
| Who reviews the plan | **The model** reviews and improves its own plan. |
| Approvals | **The user approves the reviewed plan once**; that approves the plan's change commands and file changes. |
| Scope of the approval | **Only what's in the plan, and only inside the trusted folder.** |
| Answers to a plan | **Approve**, **Revise with a comment** (back to planning), **Deny** (job ends). |
| A needed command that isn't in the plan | **Go back and send a revised plan** (no one-off approval). |
| Verify retries | **3** fix attempts, then stop and report. |
| What to avoid most | **Not following the plan.** |
| Commands before the plan | **Harmless checks are OK** (tool versions), and **system/environment/tool info is cached**. |
| While a job runs | **Live progress** in the chat window. |

## Design (my calls, from the conversation)

### Entry: a tool call routed by the graph

- New tool `startCodingJob(goal)` (marked so the router recognizes it; it has no Java body work of
  its own). The model calls it when a request is real coding work; small edits still use the normal
  tools.
- The main router (`AgentGraph.route`) sends a reply containing a `startCodingJob` call to a new
  `coding` subgraph node, in the same way it routes to `trusted` / `approval` today.
- When the subgraph ends, it answers that tool call with a `ToolExecutionResultMessage` containing
  the job report; the graph then returns to `agent`, which answers the user. So the main
  conversation sees exactly one tool call and its report, not every internal step.

```
START -> memory -> agent --(startCodingJob)--> coding -> agent
                         --(… existing routes …)
coding = subgraph:
  environment                              (cached tool versions; probes if stale, no model)
  -> investigate <-> investigateTools      (read-only tools + probe commands, ReAct loop until findings)
  -> plan -> review -> ⏸ planApproval      (interrupt; user: approve / revise(comment) / deny)
       approve -> implement <-> implementTools   (only calls covered by the plan run)
                  unplanned call -> plan          (revise; back to ⏸ planApproval)
               -> verify --pass--> report -> END
                         --fail, attempts < 3--> implement
                         --fail, attempts = 3--> report -> END
       revise  -> plan
       deny    -> report -> END
```

### State (new keys in `AgentGraph.State`, used only by the subgraph)

- `codingGoal` — the goal from the `startCodingJob` call.
- `codingEnvironment` — the environment summary from the `environment` node.
- `codingMessages` — the job's own transcript (appender), separate from the main `messages`, so the
  model's planning and tool chatter stays out of the conversation and summary memory.
- `codingFindings` — investigation results (text).
- `codingPlan` — the current plan as JSON: ordered steps, each with a description, the commands it
  will run, the files/folders it will create or change (paths relative to the trusted folder; a
  folder entry covers everything under it), plus the verify commands for the job.
- `codingPlanDecision` — written by `Agent` on resume: approve / revise + comment / deny (same
  mechanism as `approvals` today: interrupt before `planApproval`, `updateState`, resume).
- `codingStep` — index of the current step; steps are worked in order and marked done.
- `codingAttempts` — verify attempts used (max 3).
- `codingReport` — the final report (plan vs. done, verify output, what's still broken).

### Environment info (decided with the user: harmless checks are OK, and cached)

- A new first node in the subgraph, **`environment`**, runs before `investigate`. It doesn't use the
  model: it loads the cached environment info, or, if there is none or it's older than 7 days
  (my call), runs a fixed list of harmless probe commands and stores the results.
- Probe list (my call; each with a short timeout, missing tools are recorded as "not installed"):
  OS / shell / home (as `systemInfo`), `java -version`, `javac -version`, `gradle --version`,
  `mvn -v`, `node --version`, `npm --version`, `git --version`, `python --version`,
  `docker --version`.
- Cache file: `~/chat/environment.json` (next to `settings.json`), with the time of the check.
  It's refreshed when stale, and also when a verify failure says a tool is missing (my call).
- The environment summary goes into the job state (`codingEnvironment`) and into the prompts of
  investigate, plan and review, so plans use the installed versions and the right shell.
- **During investigate**, the model may run commands **only** from that probe list (exact match)
  or the user's trusted commands, without asking. No other commands run before the plan is approved.

### Plan entries (my calls, after the builder check)

- **Commands** are `{command, workingDirectory}` pairs; `workingDirectory` is relative to the
  trusted folder and must resolve inside it (`WorkFolder.resolveInside`). A call matches only with
  the **exact** command text (whitespace-normalized) **and** the same working directory. **No
  wildcards** in plans. Shell syntax (`&&`, `|`, `$env:`…) is allowed in a plan command because the
  user approves the exact text; it is matched exactly, never as a prefix. A planned command may run
  any number of times (e.g. rebuilding during fixes).
- **File entries** carry a kind: `create/modify` (a file, or a folder covering everything under it)
  or `delete` / `move` (only these allow `deletePath` / `movePath` on that path). A folder entry
  never allows deleting or moving the folder itself.
- **Long-running commands:** commands run by a coding job use `CODING_COMMAND_TIMEOUT_SECONDS`
  (default 600) instead of the 60 s default. Commands still get no input, so the review step must
  require non-interactive flags (e.g. `npx sv create … --template minimal --no-add-ons`,
  `gradle init --type java-application --dsl kotlin …`).
- **The user's trusted commands** (global + conversation) still run during a job without being in
  the plan; everything else unplanned triggers a revision.

### Verify and fixes (my calls)

- A fix may change files and run commands that are already covered by the plan. Anything new →
  revised plan → user approval, then implementation continues.
- The 3 verify attempts are counted for the **whole job** (a re-plan doesn't reset them).
- During fixes `codingStep` stays at the end of the plan (all steps done); the fix context is the
  failing verify output.

### Report persistence (my call)

- The `startCodingJob` tool result contains the final plan (with done/skipped marks) and the report
  as Markdown, so they're saved with the conversation and still viewable after reopening; the chip
  opens that text in the side panel.

### Enforcement of the plan

- During `implement`, the model gets the normal tool specifications. Before a call runs,
  `implementTools` checks it against the approved plan (and the trusted folder):
  - read-only tools always run;
  - a command matching one of the plan's commands, or a file change whose path is listed (or under
    a listed folder), runs **without** the usual per-call approval;
  - anything else does not run: the subgraph records why and routes to `plan`, which produces a
    revised plan (keeping done steps) that goes through `review` and `planApproval` again.
- The check reuses the existing matching code (`TrustedCommands` for commands; `WorkFolder` for
  paths). It's the same idea as trusted commands, scoped to the job and stored in the job's state,
  so it ends with the job.
- Web content: if a coding job reads web content (docs via `fetchPage`), the plan approval still
  covers the plan's items (the user approved them explicitly); unplanned calls still trigger a
  revision. *(My call; the existing web rule is about unasked actions, and the plan check covers
  that.)*

### Plan approval UI

- `Agent` treats the pause before `planApproval` like the approval pause today, through an extended
  `Approver` callback for plans.
- Chat window: a dialog showing the plan rendered as Markdown (steps, commands, files, verify
  commands) with **Approve**, **Revise** (opens a comment field; the comment goes to `plan`) and
  **Deny**.
- CLI: prints the plan; answers `y` (approve), `r <comment>` (revise), anything else (deny).

### Live progress

- `Agent.run` switches from `graph.invoke` to `graph.stream`, which yields one output per finished
  node; each is turned into a progress event (phase, step n/m, current command, verify attempt n/3)
  and passed to a progress callback.
- The chat window shows a progress card in the transcript that updates live and becomes the job's
  summary chip when done (clicking opens the report/plan in the side panel).
- The stream is cancellable; a Stop button is a natural follow-up but not part of this work.

### Prompts

- Each phase has its own system instructions (investigate: read and summarize what exists; plan:
  output the plan JSON; review: check for missing steps, wrong order, commands that won't work on
  this OS, files outside the folder, and output the corrected plan; implement: do the current step
  only; verify: run the plan's verify commands). The plan format is validated; invalid JSON goes
  back to `plan` once with the parse error.

## Left to the builder

- Exact JSON schema of the plan and the exact prompt wording.
- How the investigate loop decides it has enough (e.g. a step limit plus the model saying "done").
- Progress card styling; the side-panel layout for plan/report.
- Test strategy details (fake `ChatModel` graph tests like `SummaryMemoryTest`, plus unit tests for
  the plan check).
- Whether `codingMessages` is cleared or kept after the job (it is not shown to the user).
